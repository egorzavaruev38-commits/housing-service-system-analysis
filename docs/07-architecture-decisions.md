# Архитектурные решения

## ADR 01 Transactional Outbox

**Статус:** принято.  
**Контекст:** прямой вызов уведомлений после commit может потеряться, а вызов до commit может отправить сообщение об операции, которая затем откатится.  
**Решение:** сохранять бизнес-изменение и outbox-событие в одной транзакции.  
**Последствия:** нужна фоновая доставка, мониторинг очереди и дедупликация у получателя.

## ADR 02 Идемпотентность создания

**Статус:** принято.  
**Контекст:** мобильный клиент может повторить запрос после timeout и не знает, была ли первая попытка успешной.  
**Решение:** использовать `Idempotency-Key`, хеш нормализованного тела и сохраненный результат операции.  
**Последствия:** требуется срок хранения ключа и правило конфликта для другого тела.

## ADR 03 Оптимистическая блокировка

**Статус:** принято.  
**Контекст:** диспетчер и мастер могут одновременно менять одну заявку.  
**Решение:** клиент передает версию через `If-Match`, обновление выполняется только при совпадении версии.  
**Последствия:** клиент должен перечитать заявку после `409 VERSION_CONFLICT`.

## ADR 04 Файлы вне сервиса заявок

**Статус:** принято.  
**Контекст:** бинарные файлы увеличивают нагрузку на основной API и базу.  
**Решение:** хранить в заявке только метаданные и URL объекта в файловом хранилище.  
**Последствия:** нужны проверка допустимых URL, срок жизни загрузки и антивирусная обработка на стороне файлового сервиса.

## ADR 05 SQLite для прототипа

**Статус:** принято только для портфельного проекта.  
**Контекст:** проверка должна воспроизводиться локально без инфраструктуры.  
**Решение:** использовать SQLite и стандартную библиотеку Python.  
**Последствия:** при миграции на PostgreSQL потребуются повторная проверка типов, конкурентности, индексов и SQL-диалекта.
