# Требования

## Бизнес требования

- **BR-01.** Все обращения жителей регистрируются в единой системе.
- **BR-02.** Повторная отправка одного запроса не создает вторую заявку.
- **BR-03.** Участники процесса видят актуальное состояние заявки и историю изменений.
- **BR-04.** Сбой уведомлений не отменяет успешно сохраненную бизнес-операцию.
- **BR-05.** Действия можно связать между системами с помощью correlation ID.

## Функциональные требования

- **FR-01.** Система принимает заявку с категорией, описанием, жителем, объектом и признаком аварийности.
- **FR-02.** Система проверяет обязательные поля и типы данных до сохранения.
- **FR-03.** Система возвращает прежний результат при повторе запроса с тем же `Idempotency-Key` и тем же телом.
- **FR-04.** Система отклоняет повтор ключа идемпотентности с другим телом ошибкой `409`.
- **FR-05.** Система позволяет получить заявку по внутреннему ID.
- **FR-06.** Система возвращает список заявок с фильтрами и постраничной выдачей.
- **FR-07.** Диспетчер назначает активного мастера на заявку.
- **FR-08.** Уполномоченный пользователь меняет статус только по допустимому переходу.
- **FR-09.** При изменении статуса система сохраняет автора, время и комментарий.
- **FR-10.** После создания заявки и изменения статуса система формирует outbox-событие.
- **FR-11.** Система принимает метаданные вложений и связывает их с заявкой.
- **FR-12.** API возвращает ошибки в едином формате с `correlation_id`.

## Нефункциональные требования

- **NFR-01. Доступность.** Месячная доступность API — не ниже 99,5% без учета согласованных работ.
- **NFR-02. Производительность.** 95-й перцентиль ответа на создание и чтение заявки — не более 500 мс без учета внешнего файлового хранилища.
- **NFR-03. Надежность.** Событие outbox не теряется после подтвержденной транзакции создания или смены статуса.
- **NFR-04. Идемпотентность.** Ключ создания хранится не менее 24 часов.
- **NFR-05. Конкурентность.** Устаревшая версия заявки не может перезаписать более новое состояние.
- **NFR-06. Наблюдаемость.** Логи содержат timestamp, service, level, correlation ID, operation ID и код результата без чувствительных данных.
- **NFR-07. Безопасность.** Доступ к операциям определяется ролью; токены, cookies и персональные данные не записываются в открытые логи.
- **NFR-08. Аудит.** История статусов не изменяется через публичный API.
- **NFR-09. Совместимость.** Контракт API описан в OpenAPI 3.1, время — ISO 8601, кодировка — UTF-8.

## Ограничения

- прототип БД выполнен на SQLite для локальной воспроизводимости;
- денежные операции отсутствуют;
- все данные в репозитории синтетические;
- бинарные файлы хранятся вне сервиса заявок.
