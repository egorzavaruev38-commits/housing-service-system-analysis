# Контекст и границы системы

## Проблема

Заявки жителей поступают по разным каналам, из-за чего обращения дублируются, статусы обновляются несогласованно, а история действий теряется. Диспетчеру трудно видеть актуальную очередь, мастеру — получать однозначное назначение, жителю — понимать текущее состояние обращения.

## Цель MVP

Создать единый процесс регистрации и обработки заявки: принять структурированные данные, проверить их, сохранить заявку, назначить исполнителя, контролировать переходы статусов и подготовить надежную отправку уведомлений.

## Заинтересованные стороны

| Сторона | Потребность |
|---|---|
| Житель | Создать обращение один раз и видеть его состояние |
| Диспетчер | Проверять очередь и назначать мастера |
| Мастер | Получать назначенные заявки и менять их статус |
| Администратор | Управлять справочниками и разбирать сбои |
| Сервис уведомлений | Получать события в согласованном формате |
| Служба поддержки | Восстанавливать цепочку действий по correlation ID |

## В границах MVP

- создание и просмотр заявки;
- фильтрация списка по статусу, приоритету и исполнителю;
- назначение мастера;
- изменение статуса по допустимому переходу;
- история статусов;
- метаданные вложений без хранения бинарного файла;
- защита создания от повторного запроса;
- формирование событий для уведомлений;
- единая модель ошибок API.

## Вне границ MVP

- мобильное приложение и пользовательский интерфейс;
- биллинг и оплата работ;
- оптимизация маршрутов мастеров;
- распознавание изображений;
- фактическое хранилище файлов;
- отправка SMS, push или email;
- интеграция с реальной CRM.

## Внешние системы

- портал жителя — создает и читает заявки;
- рабочее место диспетчера — управляет очередью и назначениями;
- приложение мастера — получает задачи и меняет статус;
- сервис уведомлений — принимает события асинхронно;
- файловое хранилище — выдает URL загруженных файлов.

## Предположения

- житель уже аутентифицирован, а его идентификатор доступен сервису;
- справочники категорий и жилых комплексов согласованы заранее;
- время передается в ISO 8601 с часовым поясом;
- один мастер может иметь несколько активных заявок;
- аварийная заявка получает приоритет `critical`, если оператор не установил более строгое правило.
