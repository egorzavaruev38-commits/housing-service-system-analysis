# Система обработки заявок жилого комплекса

Учебный проект по системному анализу. Я взял знакомый бытовой процесс: житель оставляет заявку о неисправности, диспетчер назначает мастера, а мастер меняет статус работы.

Цель проекта — пройти основные этапы работы системного аналитика на одном примере: определить границы системы, собрать требования, описать API и данные, продумать ошибки и проверить основные сценарии.

## Что есть в проекте

- контекст системы, участники и границы MVP;
- бизнес-, функциональные и нефункциональные требования;
- Use Case для создания заявки, назначения мастера и смены статуса;
- критерии приемки и тестовые сценарии;
- REST API в формате OpenAPI 3.1;
- схема SQLite, тестовые данные и несколько SQL-запросов;
- диаграммы процесса, состояний, последовательности и ER-модель.

## Несколько принятых решений

- При повторной отправке запроса используется `Idempotency-Key`, чтобы не создавать дубли.
- История статусов хранится отдельно от самой заявки.
- Уведомления описаны через outbox-события: ошибка сервиса уведомлений не должна отменять уже сохраненную заявку.
- Версия заявки используется для защиты от одновременного изменения диспетчером и мастером.

## Локальная проверка

Нужен Python 3.11 или новее, устанавливать дополнительные библиотеки не требуется.

```bash
python scripts/validate_project.py
```

Скрипт проверяет JSON-примеры, основные поля OpenAPI и запускает схему с тестовыми данными в SQLite.

## Что пока не реализовано

Это не готовый сервис, а аналитическая проработка. В проекте нет интерфейса, авторизации, настоящего файлового хранилища и отправки уведомлений. SQLite выбран для простого локального запуска. В следующей версии я бы добавил роли пользователей, подробнее описал интеграцию с файловым сервисом и проверил схему на PostgreSQL.

Все имена, адреса и идентификаторы в примерах вымышлены.
